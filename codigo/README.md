# Alejandro Curcio — sitio personal

P0 scaffold. Astro 5 + Tailwind, content sourced from the vault at
`../` (the folder this `sitio/` directory lives inside — treat it as the CMS).

## Stack

- **Astro 5** (`astro@5.18.2`), minimal template — no UI framework, no
  component library.
- **Tailwind CSS 3** via `@astrojs/tailwind`. `applyBaseStyles` is off:
  `src/styles/tokens.css` owns the reset and CSS custom properties instead of
  Tailwind's preflight, so there's one source of truth for base styling.
- **Runtime:** [Bun](https://bun.sh) preferred (`~/.bun/bin/bun`); Node 22+
  works too, all scripts are plain Node-compatible ESM.

## Run it

```sh
bun install       # or: npm install
bun run dev        # or: npm run dev  — http://localhost:4321
bun run build       # production build -> dist/
bun run preview      # serve the production build locally
```

## Content comes from the vault (vault = CMS)

The knowledge vault lives one directory up, at `../` (i.e. `Página Ale/`,
the parent of `sitio/`). It's a folder of human-written Markdown notes
(Obsidian-style, with `[[wiki links]]` and YAML frontmatter) — that vault
is the CMS for this site. `sitio/` never edits it; it only reads from it.

`scripts/ingest.mjs` parses these vault files:

| Output | Vault source(s) |
|---|---|
| `src/data/quotes.json` | `Alejandro/Libros/Capital de Vida/Citas — Capital de Vida.md`, `Alejandro/Libros/Toolbook/Citas — Toolbook.md`, `Alejandro/Frases Destacadas.md` |
| `src/data/timeline.json` | `Alejandro/Cronología de Hitos.md` |
| `src/data/press.json` | `Prensa/Índice de Prensa.md` (the markdown table) |
| `src/data/books.json` | `Alejandro/Libros/Capital de Vida.md`, `Alejandro/Libros/Toolbook.md`, `Alejandro/Libros/CEO de tu Vida.md` |

### Re-running ingestion

Whenever the vault content changes, regenerate the JSON:

```sh
bun run ingest     # or: npm run ingest / node scripts/ingest.mjs
```

This overwrites `src/data/*.json` and prints a per-file count plus any
parsing warnings to the terminal. The vault markdown is human-written and
its shape can drift over time (headings renamed, a quote format tweaked,
etc.) — the parser is defensive: it skips anything it can't confidently
parse and logs a `[warn]` line for it rather than crashing. **Always check
the warnings after re-running ingestion**, especially after someone edits
the vault files directly.

### Why JSON files instead of Astro content collections

This is a P0 hackathon scaffold and the vault's shape isn't stable yet.
Content collections need an upfront schema; flat JSON under `src/data/` is
importable directly from any `.astro` file with zero config and doesn't
force a schema commitment before the content settles. Revisit this once
the vault structure is stable — migrating JSON to content collections
later is a small, mechanical change, not a rewrite.

## Design tokens

`src/styles/tokens.css` holds every color, font, radius and spacing value
as a CSS custom property (`--color-primary`, `--font-heading`, etc.), each
flagged `TODO(P1)` — **these are neutral placeholders**, not a design
decision. The real palette and type pairing come out of the P1 design
tournament.

`tailwind.config.mjs` maps Tailwind's theme (`bg-primary`, `text-accent`,
`font-heading`, …) onto those same custom properties. So:

- Reskinning the whole site is a **one-file edit**: change the values in
  `tokens.css` (or repoint `--font-heading`/`--font-body` at new
  `@font-face` declarations) and every component using the Tailwind
  classes or the custom properties directly picks it up.
- Component code should never hardcode a hex color, font stack, or pixel
  radius — always go through a token (either the CSS custom property or
  its Tailwind class mapping).

## What's not here yet (by design — P0 scope)

- No header/nav/footer chrome — added once P1 picks a design direction.
- No real page design — `index.astro` only proves the ingestion pipeline
  works (it renders live counts from `src/data/*.json`).
- No fonts loaded — `Base.astro` has a placeholder comment marking where
  they go once chosen.
- No content collections / schema validation — see "Why JSON files" above.

## Preguntale a Ale (P4b — RAG chat)

`/preguntale` is a small retrieval-augmented chat over Alejandro's books and
press archive. Everything that needs the OpenRouter key or the embedding
vectors runs server-side; the browser only ever talks to `/api/chat`.

- **RAG data**: `src/chat-data/chunks.json` + `src/chat-data/index.json`
  (319 chunks / 1536-dim OpenAI `text-embedding-3-small` vectors), plus
  `system-prompt.md` and `chat-config.json` — all copied verbatim from
  `../sitio-chat/`. They live under `src/`, **not** `public/`, so the
  vectors and the persona prompt never ship to the client bundle; only the
  server-side `/api/chat` endpoint reads them (see
  `src/lib/rag.js`).
- **Rendering mode**: the site stays `output: 'static'` (every other page
  still prerenders to plain HTML at build time). `src/pages/api/chat.js`
  opts itself out with `export const prerender = false`, which is Astro
  5's supported way to mix a handful of on-demand routes into an otherwise
  static site. That still requires an adapter to be configured project-wide
  even though only one route uses it — hence `@astrojs/node` (`mode:
  'standalone'`) in `astro.config.mjs`. `astro dev` runs this endpoint
  natively; `astro build && node ./dist/server/entry.mjs` (or
  `bun run preview`) is the production path.
- **Env**: `.env` holds `OPENROUTER_API_KEY` (already listed in
  `.gitignore`, and this repo isn't a git repo yet at all). If it's ever
  missing/empty, `/api/chat` returns a clear developer-facing error instead
  of a silent failure — see the "graceful errors" section in
  `src/pages/api/chat.js`.

```sh
bun run dev   # http://localhost:4321/preguntale
```
